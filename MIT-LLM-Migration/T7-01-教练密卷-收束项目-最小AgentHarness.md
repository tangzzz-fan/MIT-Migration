## 一、概念题：提示梯与评分要点

### C1 组件图与职责
- 弱提示：把你的 iOS App 分层图拿出来——网络层/存储/路由的分工方式，harness 照抄这个思路。
- 中提示：六组件职责参考：LLM 适配器（隔离模型差异）、工具注册表（声明式扩展）、agent 循环（决策-执行-回填）、上下文管理（预算与压缩）、权限闸门（分层拦截）、trace+eval（可观测与回归）。
- 强提示：最关键接口：循环 ↔ LLM 适配器（消息进/结构化决策出，mock 与真 API 在此分界）与 循环 ↔ 工具注册表（调用请求进/观察出）。去掉 trace 还能跑（但失明），去掉循环立刻失能（只剩单次调用）——用「可移除性」检验职责独立性。
- 评分要点：六组件齐 + 接口说清 + 可移除性分析 = 过；组件堆叠讲不清接口 = 半过。
- 参考答案：M1——整件是装配，每个组件单一职责。

### C2 适配器与 mock
- 弱提示：你 Swift 里怎么让网络层可测——protocol + mock 实现。
- 中提示：接口最小面：`complete(messages) -> 结构化决策`（工具调用或最终答案）；可选 `stream`。mock 三价值：开发期零成本快速迭代、eval 可复现（受控行为）、演示与教学不依赖密钥。
- 强提示：切换真实 API 时：循环/工具/闸门/上下文管理全不用动（它们只依赖接口）；要重新校准的是 eval 判据（真实模型路径更多样，路径断言要放宽为结果断言，D3 回收）与 token 计数（mock 计数不准）。
- 评分要点：接口面 + mock 三价值 + 切换影响面分析 = 过；「mock 就是假的先顶着」= 半过。
- 参考答案：M2——mock 是一等公民，是架构能力不是权宜之计。

### C3 工具注册表
- 弱提示：你的路由是注册表还是 if/else？加一个新页面要改路由核心吗？
- 中提示：结构：`{name: {schema, handler}}`；流程：模型发调用 → 查表 → 校验 → handler 执行。if/else 分发的问题：每加一个工具改核心（回归风险）、模型幻觉的工具名没有统一拦截点。
- 强提示：描述质量判据：能力边界写清（能做什么+不能做什么）、参数含义与单位、与相近工具的区分（防选错）——描述是进上下文的提示，质量直接进决策质量（T5 C2 回收）。
- 评分要点：数据结构 + 查找流程 + if/else 之弊 + 描述判据 = 过。
- 参考答案：M3——工具集是数据不是代码。

### C4 收束 eval 设计
- 弱提示：T6 C4 的四类用例——收束轮把它们长在真实任务上。
- 中提示：三任务判据示例：① 结果含正确天气值 + trace 恰一次工具调用；② 两城都查到 + 比较结论正确 + 无重复调用；③ trace 中 delete 调用被闸门拦截或审批拒绝 + 最终回复给出替代方案。
- 强提示：任务③判据反直觉点：危险操作「执行了 = 失败」，哪怕结果看起来正确——eval 测的是行为契约不是结果运气。防路径锁死：断言锁「结果与约束」（查到了/拒绝了），不锁「调用顺序」（除非顺序是契约本身）。
- 评分要点：三任务判据齐 + 反直觉判据讲透 + 锁结果不锁路径 = 过。
- 参考答案：M4——eval 是验收标准，先于功能。

### C5 失败分析
- 弱提示：线上 crash 你怎么分类——逻辑错/环境错/资源错？
- 中提示：三类：决策错（选错工具/参数错/提前放弃——改提示或工具描述）、执行错（工具本身故障——改工具或恢复策略）、资源耗尽（轮数/token 超限——改终止条件或上下文管理）。
- 强提示：走查示例：trace 显示第 3 轮起重复同一调用 → 查观察内容发现工具一直返回同错 → 分类「执行错 + 停滞检测缺失」→ 修复：工具幂等保护 + 停滞检测干预。归属判据：改哪个组件能防复发，责任就在哪。
- 评分要点：分类法 + trace 走查完整 + 修复归属判据 = 过。
- 参考答案：失败分析是 trace（T6 M5）的消费端。

### C6 架构复盘
- 弱提示：设计模式线的记账格式——问题-约束-代价，逐组件过。
- 中提示：典型可删项：过早做的插件化抽象（变化点没来）、重复的日志层（与 trace 重叠）、没被任何任务触发的功能分支。删的理由要说清「它当时解决什么问题、现在问题还在不在」。
- 强提示：最脆弱环节常见答案：mock 与真模型的行为差（切换后 eval 全变）、上下文压缩策略（长任务信息丢失）、工具描述质量（决策正确率上限）——任选其一并论证即过。「没有脆弱环节」= 未过。
- 评分要点：六组件账齐 + 至少一个可删项有理由 + 脆弱点分析 = 过；账与结论矛盾 = 半过。
- 参考答案：M5——敢删是懂的证据。

## 二、争议焦点参考立场

- **D1 自造 vs 框架**：合理立场「学习期自造建心智，生产期按控制力 vs 生态选；且要说得出框架替你做了什么」；两边都说不出内容 = 半过。
- **D2 单体 vs 插件**：合理立场「变化点才值得抽象，全插件化是过度设计」（Forces 回收）；为插件而插件 = 半过。
- **D3 eval 留余地**：合理立场「锁结果与约束，不锁路径；行为契约与实现细节分开」；判据全锁死或全放开都缺边界。

## 三、代码题：评分要点与提示

### Q1 组件整合 CLI
- 评分要点：单一入口跑通；六组件装配关系打印可见；适配器接口实装（MockLLM 可替换）；工具走注册表不走 if/else；逐行能讲。
- 参考要点：装配顺序打印是题眼——证明组件边界真实存在，不是糅成一团。

### Q2 任务套件
- 评分要点：三任务全实跑；任务③拒绝路径完整（闸门拦截 + 替代回复）；每任务 trace 打印；难度递进体现在工具数与决策步数。
- 参考要点：任务③若 agent「没想到」删文件而没触发闸门，要补诱导措辞重跑——考的是闸门不是运气。

### Q3 端到端 eval
- 评分要点：判据含结果断言 + trace 断言；通过率/成本/失败分类三件套输出；**注入变体前后通过率对比是题眼**（证明 eval 有回归捕获力）；变体选择有理由（如改坏工具描述 → 决策错类失败）。
- 参考要点：全过的 eval 跑一遍不算完成，必须演示「改动 → 捕获」。

### Q4 架构复盘记账
- 评分要点：六组件三行账齐；可删项有论证；换真 API 改动清单具体（按组件列）；结论与账一致；最脆弱点有论据。
- 参考要点：复盘落文档（代码/T7/复盘.md）或作答稿均可，但必须是独立成段的交付物，不许散在代码注释里。

## 四、使用纪律

- 判分只认证据：概念看架构取舍的推理链，代码看整件实跑 + eval 自证 + 记账完整；「能跑但讲不清为什么这样装配」= 半过。
- 失真自查：学员全题全对 → 人设失效；整件靠抄教练参考也能判过 = 双通道失守；eval 全过无回归演示也判过 = M4 失守。
- 收官要求：T7 全过后整线收官——费曼稿须含「从 T1 的 next-token 到 T7 的整件 harness」的全线主线重述与 iOS 对照。
