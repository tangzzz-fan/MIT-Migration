# T5 教练出题集：Agent 循环与工具调用

> 本轮从「一问一答」进「自主循环」：模型从答题者变成决策者。原料 = 学员状态机/delegate/事件循环存量 + T3 消息协议（tool 角色登场）。
> 学员人设：预期在「agent 当 if-else 自动化、循环终止缺失、工具报错直接崩、分不清 workflow 与 agent」上暴露漏洞。
> 使用纪律：卡住按「弱→中→强」逐级提示（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | iOS 存量锚点 |
|---|------|-----------|------------|
| M1 | agent = 模型决策 + 工具执行 + 循环 | 三要素缺一即不是 agent：模型决定「下一步做什么」（不是代码写死），工具把决定变成对世界的动作，循环把结果喂回去直到完成 | 事件循环 + delegate：只是「事件处理器」换成了模型 |
| M2 | function calling = 类型化的调用契约 | 工具以 JSON schema 声明（名字/参数/描述），模型输出结构化调用请求，宿主解析执行——模型从不直接执行，只「提议」 | 像 protocol 方法签名：模型只能发出符合签名的调用，宿主才是实现方 |
| M3 | 观察回填 = 循环的燃料 | 工具结果（含报错）作为 tool 消息进上下文，成为下一轮决策的输入；没有回填就没有循环，只有单次调用 | 像异步回调：结果回来才能走下一步，错误也是结果 |
| M4 | 终止条件是一等公民 | 成功信号（模型宣布完成）+ 硬上限（最大轮数/token 预算）+ 停滞检测（重复同一动作）——三者缺一，循环就可能烧钱空转 | 像重试预算 + 超时：网络层没人敢写无限重试 |
| M5 | workflow 与 agent 的分界 = 谁在决策 | 路径由代码写死 = workflow（可控、可预测）；路径由模型运行时选择 = agent（灵活、难预测）；多数业务先 workflow，不确定时才上 agent | 像硬编码路由 vs 动态调度：能用 switch 解决就别上运行时反射 |

学员自检要求：合上表复述 M1–M5，并用 M5 判一个你见过的「AI 自动化产品」到底是 workflow 还是 agent。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 多 agent 协作是进步还是过度设计？**
- 正方：角色分工（规划者/执行者/评审者）带来上下文隔离与专精，复杂任务可分解。
- 反方：agent 间通信本身引入新的错误传播与成本叠加，很多「多 agent」只是把提示拆成了几段；单 agent + 好工具常常更强。
- 对迁移者的意义：判据是「上下文隔离与分工是否真的降低了单 agent 的负担」——为架构而架构在 agent 领域同样成立（呼应设计模式线的反滥用纪律）。

**D2 ReAct（边想边做）vs Plan-and-Execute（先规划后执行）**
- ReAct 派：每步都拿最新观测决策，适应变化；Plan 派：先出全局计划再执行，省调用、易审计。
- 实际共识在中间：计划可以随观测修订（replan），纯任何一种都有失败模式。
- 对迁移者的意义：给出「任务可预见性」作为选型维度，而不是背流派。

**D3 该给模型多大自由度？**
- 宽松派：限制越多 agent 越废，靠模型自身判断 + 事后审计。
- 约束派：工具白名单、参数校验、危险操作审批是刚需，自由度是设计出来的不是放出来的。
- 对迁移者的意义：这是 T6 权限闸门前哨——你的 iOS「最小权限」直觉在这里直接可用。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只会调框架 API = 不过。

### C1 agent 的最小结构是什么？它和「自动化脚本」的本质区别在哪？

问题：画出（或口述）agent 循环的最小闭环，指出三个不可省略的组件；然后论证：一个写死步骤的「调 LLM 三次」的脚本为什么不是 agent？「模型决策」具体改变了什么（路径空间、失败模式、测试方式各说一条）。

### C2 function calling 为什么需要 schema？没有 schema 会怎样？

问题：解释工具 schema（名字/参数类型/描述）对模型的三重作用；推演：如果只给模型一段自然语言工具说明、让它自由输出调用文本，会多出哪两类故障（解析侧与行为侧）？schema 里的「描述」字段为什么不是可有可无的？

### C3 工具执行失败了，agent 该怎么办？

问题：对比三种策略：直接崩溃 / 静默重试 / 把错误作为观察回填让模型决策；论证为什么第三种是 agent 的正确姿势（从 M3 推）；再给出回填的边界：什么样的错误不该让模型处理（要熔断/上报的）。

### C4 循环什么时候停？只有「最大轮数」够吗？

问题：给出至少三种终止机制并说明各防什么失控；构造一个「轮数没到但已经空转」的场景（重复同一工具调用），说明停滞检测怎么设计；token 预算为什么也应该进终止条件。

### C5 workflow 和 agent 怎么选？

问题：这是争议题 D1/D2 的落地。给出你的判据（至少两条，如任务路径的可预见性、错误的代价）；举一个「应该从 agent 退回 workflow」的例子和一个「workflow 撑不住必须上 agent」的例子。

### C6 多轮工具调用的「状态」住在哪里？

问题：agent 跑了 8 轮，第 9 轮需要第 2 轮的信息——这份状态可能在哪些地方（上下文/外部存储/工具自身）？各自的限制是什么（用 T1 M4 + T4 M5 推）？为什么「全靠上下文」在长任务里会出事？
