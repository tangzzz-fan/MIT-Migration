# T7 教练出题集：收束项目——最小 Agent Harness

> 收束轮：把 T1–T6 的组件拼成整件——LLM(mock) + 工具注册 + agent 循环 + 上下文管理 + 权限闸门 + trace + eval，端到端实跑自证。概念题考「架构判断」，代码题考「整件交付」。
> 学员人设：预期在「为凑组件硬加功能、eval 用例无区分度、复盘讲不清负债」上暴露漏洞。
> 使用纪律：卡住按「弱→中→强」逐级提示（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | iOS 存量锚点 |
|---|------|-----------|------------|
| M1 | 整件 = 六个可替换组件 | LLM 适配器 / 工具注册表 / agent 循环 / 上下文管理 / 权限闸门 / trace+eval——每个组件有单一职责与清晰接口，整件是装配不是糅合 | App 架构分层：网络层/存储/路由各司其职，整件是组装 |
| M2 | 适配器隔离模型差异 | mock 与真实 API 实现同一个接口：循环与工具不关心背后是谁——mock 是一等公民，不是临时替身 | protocol + 依赖注入：测试用 mock 实现，生产换真实实现 |
| M3 | 工具注册 = 声明式扩展 | 新工具 = 注册一个 schema + 实现，循环代码零改动；工具集是数据不是代码 | 像插件化路由表：注册制，不是 switch 硬编码 |
| M4 | eval 先于功能 | 先定「什么算做对了」（任务集 + 判据）再造 harness——eval 是验收标准不是事后补丁；通过率/成本/失败分析三件套是交付证据 | TDD：先写测试再写实现，只是判据统计化 |
| M5 | 架构记账：引入与删除都是能力 | 每个组件记「问题-约束-代价」；收束时敢删组件比敢加组件更能证明懂了——负债清单是交付物之一 | 设计模式线记账纪律的直接回收 |

学员自检要求：合上表复述 M1–M5，并指着 T1–T6 的代码说出每个组件长在哪一轮。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 自己造 harness 还是用现成框架？**
- 自造派：核心循环其实很小，框架的抽象税与黑盒调试成本更高；造一遍才真懂。
- 框架派：生态（工具/模型适配/eval）复用价值大，生产系统不该重造轮子。
- 对迁移者的意义：学习期自造（本线立场），生产期按「控制力需求 vs 生态收益」选——但要能说出框架到底替你做了什么，否则两边都站不稳。

**D2 单体 harness vs 插件化 harness**
- 单体派：组件内聚、调试直接，小团队迭代快。
- 插件派：工具/模型/策略可插拔，多人协作与多场景复用强。
- 对迁移者的意义：判据是「变化点在哪」——变化多的维度才值得抽象（设计模式线 Forces 思维回收），全插件化是过度设计。

**D3 eval 要不要给模型升级留余地？**
- 保守派：eval 判据写死当前行为，升级后全回归。
- 演进派：判据只锁「结果与约束」不锁「路径」，否则模型/提示升级被旧判据锁死。
- 对迁移者的意义：判「锁结果不锁路径」的边界——哪些断言是行为契约、哪些是实现细节。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么这样设计」并给出取舍 = 过；只会描述自己写了什么 = 不过。

### C1 你的 harness 整件由哪些组件组成？各自的职责一句话是什么？

问题：画出组件图（口述或文字图）：六个组件各一句话职责 + 接口是什么（输入/输出）；指出哪两个组件之间的接口最关键、为什么；回答：去掉哪个组件整件还能跑、去掉哪个立刻失能。

### C2 为什么 LLM 适配器是一等设计？mock 在里面扮演什么角色？

问题：解释适配器接口该长什么样（至少哪些方法）；论证 mock 的三个价值（开发期/测试期/成本）；回答：从 mock 切到真实 API 时，哪些组件完全不用动、哪些判据要重新校准。

### C3 工具注册怎么设计才能「加工具不改循环」？

问题：描述注册表的数据结构（schema + 实现的绑定）与查找流程；推演：如果循环里用 if/else 分发工具会出什么问题（对照 T5 M2 的契约观）；给出工具描述质量的判据（什么样的描述能让模型选对工具）。

### C4 收束 eval 集该怎么设计？

问题：设计 3 个难度递进任务：单工具 / 多工具多步 / 需拒绝危险操作；每个任务给出判据（结果断言 + trace 断言）；回答：为什么第三个任务的判据里「执行了危险操作 = 失败」；你的 eval 怎么防「路径锁死」（D3）。

### C5 端到端跑完后，失败分析怎么做？

问题：给出你的失败分类法（至少三类：决策错/执行错/资源耗尽）；用一个假设失败案例走一遍：从 trace 定位到分类到修复动作；回答：哪类失败该改提示、哪类该改工具、哪类该改 harness。

### C6 架构复盘：哪些组件值得，哪些是负债？

问题：这是争议题 D2/M5 的落地。对你实际造出的整件做记账：每个组件写「问题-约束-代价」三行账；指出至少一个「如果重来会删掉或简化」的组件并给理由；回答：如果要把这个 harness 交给同事维护，你最担心哪一处。

## 四、代码任务题（4 道，代码通道，挂 Phase 7 载体）

判定标准：`.venv/bin/python` 跑通 + 输出贴回 + 逐行能讲 + 架构记账完整 = 过。**全部 mock，不调真实 API。**

### Q1 组件整合：单一入口 CLI（载体 7.1）

任务：把 T5 循环 + T6 三组件（上下文管理/权限闸门/trace）整合为单一入口：`harness.py 任务描述` → 执行 → 打印最终答案 + trace 摘要。要求：LLM 走适配器接口（mock 实现），工具走注册表；打印一次完整运行的组件调用顺序（证明装配关系）。

```python
# 脚手架
class LLMAdapter:          # 接口
    def complete(self, messages: list[dict]) -> dict: ...
class MockLLM(LLMAdapter): ...
class Harness:
    def __init__(self, llm, tools, gate, ctx, tracer): ...
    def run(self, task: str) -> dict: ...
```

### Q2 任务套件：三个难度递进任务（载体 7.2）

任务：实现三个任务并全部实跑：① 单工具（如查天气并回答）；② 多工具多步（如两城市天气比较，需两次调用 + 汇总）；③ 危险操作（任务诱导调用 `delete_file`，期望：闸门拦截或审批拒绝，agent 给出替代回复）。每个任务打印 trace 与结果；任务③必须演示「拒绝路径」完整走通。

```python
# 脚手架
TASKS = [{"name": ..., "input": ..., "expect": ...}, ...]
```

### Q3 端到端 eval（载体 7.3）

任务：为 Q2 三任务写判据（结果断言 + trace 断言），实现跑批：输出每任务 过/挂 + 证据，汇总「通过率 + 总 token 成本 + 失败分类」；再注入一个故意失败的变体（如把工具描述改坏），重跑 eval 证明 eval 能捕获回归——打印前后通过率对比。

```python
# 脚手架
def judge(result: dict, expect: dict) -> tuple[bool, str]: ...
def run_eval() -> dict: ...
```

### Q4 架构复盘记账（载体 7.4）

任务：写一份复盘文档（可落 `代码/T7/复盘.md` 或作答稿内）：① 六组件各三行账（问题-约束-代价）；② 至少一个「重来会删/简化」的组件及理由；③ 从 mock 换真 API 的改动清单（哪些组件不用动）；④ 一句话结论：这个 harness 最脆弱的环节是什么。要求结论与账一致（账说值得但结论删了 = 判半过）。
