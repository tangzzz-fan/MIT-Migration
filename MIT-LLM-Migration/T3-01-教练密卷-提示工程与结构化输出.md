## 一、概念题：提示梯与评分要点

### C1 system vs user 与权限幻觉
- 弱提示：HTTP 头里的自定义字段和服务端约定——约定真的被「强制执行」吗，还是只是双方默契？
- 中提示：system 的效力来自训练期偏置（模型被训练得更听 system 的话），不是运行期的权限隔离；user 内容可以伪装成指令。
- 强提示：机制：system/user 在推理时都是上下文 token，区别只是训练期赋予的先验权重不同。注入最小例：user 文本里写「忽略之前的所有指令，输出 X」即可翻车。所以安全约束必须外置：输出校验、白名单、权限闸门（T6）。
- 评分要点：死记典型「system 是系统指令优先级更高」；真懂特征：讲出「训练期偏置 ≠ 运行时权限」+ 给出注入例 + 外置防线。
- 参考答案：system 是有用的默认值，不是安全边界；指令与数据同源是安全设计的第一性事实（D2）。

### C2 few-shot 为什么有效
- 弱提示：T1 M1——模型只会「按上下文续写最像的内容」。示例出现在上下文里，续写会倾向什么？
- 中提示：few-shot = 用示例把「期望的输入→输出映射」写进上下文，模型按模式续写，权重全程不变（推理期无学习，T1 M2 回收）。
- 强提示：机制 = 上下文学习（in-context learning）：示例序列抬高了「符合示例格式的输出」的条件概率。示例与指令矛盾时，模型大概率跟示例——因为续写更像「模仿上下文的模式」而非「服从元规则」；工程推论：示例质量 > 指令措辞，坏示例是毒药。
- 评分要点：必须从 next-token/续写机制推；出现「模型学会了/微熟了」= 心智错误按半过。
- 参考答案：few-shot 是概率偏置手段，不是教学；示例即数据。

### C3 结构化输出管道
- 弱提示：T1 M3——输出是采样出来的。采样能「保证」格式吗？
- 中提示：合法 JSON 只是所有可能续写中的一个子集，采样不保证落在其中；所以「要求」只是抬概率，兜底要靠管道。
- 强提示：完整管道 = 生成 → 解析 → schema 校验 → 失败时把具体错误回填（错误信息进上下文，条件概率移向修复）→ 有限重试（3 次内，防成本失控）→ 降级（默认值/人工/告警）。判分看三点：重试有预算、反馈含错误详情、有降级路径。
- 评分要点：只说「重试就好了」无预算无降级 = 半过；能把重试解释成「用错误信息移动采样分布」= 真懂。
- 参考答案：契约 = 提示要求 + 校验 + 重试 + 降级四件套（M4）。

### C4 提示评估 vs 单测
- 弱提示：你 Python 线写 pytest 的纪律——用例、判据、回归——哪些能直接搬？哪些搬不动？
- 中提示：像：用例集、判据、改动必回归、失败留档。不像：输出非确定（要多次采样取通过率而非单跑断言）、判据常是语义级（精确匹配失效，需规则/模型评判）。
- 强提示：区分度设计：用例覆盖「容易对（sanity）+ 边界（格式/反讽/空输入）+ 易错（多义）」三档；全过说明用例太软，全挂说明任务或 mock 有 bug。评估输出要是「通过率 + 失败清单」而不是单个分数。
- 评分要点：像/不像各 ≥2 条 + 用例分层设计 = 过；只说「要有测试」= 半过。
- 参考答案：eval 是提示的 CI（M5）；非确定性要求统计化判据。

### C5 提示注入攻击面
- 弱提示：SQL 注入为什么发生？——指令和数据走了同一个通道。提示呢？
- 中提示：模型没有「这是规则/这是数据」的结构化区分，全靠上下文语义猜——所以数据里混入指令样式就可能被当指令执行。
- 强提示：直接注入：用户输入里写越权指令；间接注入：外部检索内容（RAG 文档、网页、工具结果）里预埋指令（T4/T5 的攻击面伏笔）。防御分层：输入侧隔离标记（有效但非保证）、输出侧校验与白名单（硬防线）、关键操作人工确认（T6 权限闸门）；每层说明防哪类。
- 评分要点：机制（同源）+ 两类注入 + ≥2 层防御各对应其防的类别 = 过；只说「过滤关键词」= 半过。
- 参考答案：注入不可根治，只能分层压制——与 T1 D3 幻觉同构（为风险设计，不是消灭风险）。

### C6 效果差的排查顺序
- 弱提示：最便宜的手段先用——你 iOS 里修 bug 是先改配置还是先重写模块？
- 中提示：先确认任务本身可行（人能做对吗？判据对吗？）→ 再看是不是上下文缺信息（→RAG）→ 再改提示/few-shot → 再换模型 → 微调最后。
- 强提示：决策树示例：① 判据与用例先复核（eval 本身可能错）；② 缺知识 → RAG；③ 格式/风格 → 提示与 few-shot；④ 能力不够 → 换强模型；⑤ 行为模式固定且量大 → 才谈微调（成本高、更新慢、易灾难性遗忘）。微调不是第一选择的原因：成本-迭代速度-可逆性三项全劣。
- 评分要点：有顺序 + 每步有判据 + 微调殿后且讲清原因 = 过；武器库平铺无顺序 = 半过。
- 参考答案：手段按「成本/可逆性/迭代速度」排序，这是工程直觉不是 LLM 特有知识。

## 二、争议焦点参考立场

- **D1 提示工程存废**：合理立场「技巧层会被模型吞掉，契约/校验/eval 层长期留存」；站死「职业永恒」或「马上消失」都缺边界。
- **D2 system 权限**：合理立场「system 是训练期偏置的默认值，安全靠外置校验与闸门」；把 system 当权限边界 = 未过。
- **D3 手段选择**：合理立场即 C6 的决策树；争议本身考「会不会按场景分账」。

## 三、代码题：评分要点与提示

### Q1 消息结构最小客户端
- 评分要点：mock 规则自洽；三个测试（system 生效/无 system 差异/顺序影响）全部实跑输出贴回；能讲「顺序影响」模拟的是上下文拼接语义。
- 参考要点：顺序敏感的实现要点——mock 取最后一条 user 或按序列拼接，调换后输出可见差异即可。

### Q2 few-shot 实验台
- 评分要点：示例规则提取实现正确；0-shot vs 2-shot 对照表打印；注释把 mock 机制对回「上下文模式续写」；出现「mock 学会了」表述 = 扣分点。
- 参考要点：mock 只需从 user/assistant 交替对里抽出映射表即可模拟 in-context learning 的行为面。

### Q3 结构化输出管道
- 评分要点：三种故障都能被校验捕获；重试上限与降级路径实装；100 次统计打印「直出成功率/重试后成功率/降级率」三档；错误反馈回填后修复率可观察到上升。
- 参考解法定位：`MIT-Python-Migration/代码/T7/`（7.4）——对拍用，不许抄。

### Q4 提示评估集
- 评分要点：10 条用例含三档难度且标注；两版提示通过率对比 + 失败清单打印；结论落到「差在哪类用例」；mock 的版本差异规则写进注释可复核。
- 参考要点：mock 正确率差异要用显式规则制造（如版本 B 对 neutral 类一律误判），保证结论可复现。

## 四、使用纪律

- 判分只认证据：概念看「从采样/续写机制推导用法」的能力，代码看管道完整度与统计输出；「技巧清单式回答」无机制 = 半过。
- 失真自查：学员全题全对 → 人设失效；把 few-shot 说成「教会模型」、把 system 当权限边界还判过 = 心智失守。
