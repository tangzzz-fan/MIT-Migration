# T3 教练出题集：提示工程与结构化输出

> 本轮从「原理」进「用法」：T1/T2 的模型只会续写，怎么用契约让它稳定干活。原料 = 学员 Codable 数据契约/枚举建模存量 + Python 线 T7 已练旧稿（整合接管）。
> 学员人设：工程契约直觉强（预期该对）；预期在「提示工程 = 措辞玄学、few-shot 机制讲不出、校验失败只会重发」上暴露漏洞。
> 使用纪律：卡住按「弱→中→强」逐级提示（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | iOS 存量锚点 |
|---|------|-----------|------------|
| M1 | 提示 = 上下文内的接口契约 | 模型不记得你的任何约定，全部要求必须写进这一次请求的上下文；提示是「给无状态服务的接口文档」 | 像给无状态 HTTP 服务写接口约定：每次请求都要自包含 |
| M2 | 消息角色 = 分工协议 | system/user/assistant/tool 各有分工：system 定行为边界、user 给任务、assistant 留历史、tool 回观测；角色是模型训练时认的「槽位」 | 像函数签名里参数的语义标注：类型一样但职责不同 |
| M3 | few-shot = 上下文学习 | 示例不是装饰，是用「输入→输出样例」直接钉住格式与风格；模型从上下文里的模式续写，不需要改权重 | 像单元测试的 fixture：给样例比写说明书更不容易歧义 |
| M4 | 结构化输出 = 契约 + 校验 + 重试 | 要求 JSON 只是开始：解析失败/校验失败是常态，schema 校验 + 有限重试 + 降级才是完整管道 | Codable 解码失败怎么办？——同一套纪律：校验、重试、fallback |
| M5 | 提示评估 = 回归测试 | 提示是代码：改动要有 eval 集回归，两版提示用通过率对比，不接受「感觉更好」 | 改接口不跑单测 = 裸奔；改提示不跑 eval 同理 |

学员自检要求：合上表复述 M1–M5，并各举一个「提示翻车」的场景对号入座。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 提示工程是长期职业还是过渡技能？**
- 正方：模型接口长期存在「怎么说影响怎么说」，约束/评估/安全边界的工程化只会更重。
- 反方：模型越强，自然语言直说即可，精巧提示技巧会被模型理解力吞掉；长期看「提示工程师」会并入普通软件工程。
- 对迁移者的意义：无论站哪边，M4/M5（校验管道与 eval）都是不会过时的部分——争议归争议，工程基建照做。

**D2 system prompt 的权限幻觉与安全边界**
- 争议：system 被当作「管理员指令」，但它与 user 内容在模型眼里是同源的上下文——提示注入（让数据冒充指令）证明它不是权限边界。
- 正方立场：system 仍有用（行为默认值、训练期偏置）；反方立场：任何安全关键约束都不该只靠 system，要有外部校验。
- 对迁移者的意义：把「指令与数据同源」当成安全设计的第一性事实（呼应 T6 权限闸门）。

**D3 few-shot / 提示改写 / 微调 / 换模型，怎么选？**
- 各派争议在于性价比排序：few-shot 最便宜但吃上下文预算；微调改行为但成本高、更新慢；换大模型简单但贵。
- 对迁移者的意义：给出「按问题性质选手段」的决策树，而不是默认一种武器。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只能给技巧清单 = 不过。**每题要有机制维度，「我试过好用」不算回答。**

### C1 system 与 user 消息的本质区别是什么？为什么 system 不是「管理员权限」？

问题：说出两者在模型训练期与运行期各自的语义；然后论证：为什么把安全约束只写在 system 里是不充分的？举一个提示注入的最小例子。

### C2 few-shot 为什么有效？示例之间冲突了会怎样？

问题：从 T1 的 next-token 机制解释 few-shot（不许引入「模型学会了」这类说法）；再回答：如果示例格式与文字指令矛盾，模型更可能跟谁、为什么？

### C3 为什么结构化输出必须把「校验与重试」设计进管道？

问题：解释为什么「模型答应输出 JSON」不等于「输出一定是合法 JSON」（从采样机制推）；设计一个校验重试策略：重试几次、重试时给模型回传什么、预算耗尽后降级到什么。

### C4 提示评估和单位测试哪里像、哪里不像？

问题：像的地方给出至少两条（用例/判据/回归）；不像的地方给出至少两条（输出非确定、判据常需语义级）；然后设计一个 10 条用例的评估集骨架：怎么保证用例有区分度（不是全过或全挂）。

### C5 「指令与数据同源」会带来什么攻击面？

问题：解释提示注入的机制（模型无法从结构上区分「你该遵守的规则」与「你要处理的文本」）；给出至少两层防御，并说明各层防的是哪一类注入（直接注入 vs 经外部文档带入的间接注入）。

### C6 一个任务效果差，你按什么顺序排查：改提示 / 加 few-shot / 换模型 / 微调 / 加 RAG？

问题：这是争议题 D3 的落地版。给出你的决策顺序与每一步的判据（什么情况升级手段）；必须说明为什么微调不该是第一选择。
