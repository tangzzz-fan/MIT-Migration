## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | OC 迁移锚点 |
|---|------|-----------|------------|
| M1 | 度量先于优化：没有数据就没有发言权 | 先 Instruments/打点拿到瓶颈证据，再动刀；优化后同口径复测对比。旧世界结论（Time Profiler、Allocations、卡顿打点）原样迁移，新世界的变化只是**指标对象换了**（body 重算次数、actor hop、continuation 开销）——方法论本身不变 | 学员主场。唯一的新要求：给 SwiftUI/Concurrency 建立「该测什么」的新指标清单，而不是换一套方法论 |
| M2 | SwiftUI 的帧成本 = body 重算 × diff × 实际渲染，Identity 是 diff 的身份证 | body 是纯函数，状态失效 → 重算出新视图树 → 按 **Identity**（显式 id / 结构位置）配对 diff → 只重渲染变化处。Identity 变了 = 整棵子树推倒重建（状态一起丢）；body 廉价、渲染昂贵，所以「少重算」不是唯一目标，「diff 认得出谁是谁」同样要命 | UITableView 的 reuseIdentifier：复用靠「身份证稳定」；SwiftUI 的 Identity 是同一件事的声明式版本，只是身份证从你手发改成了框架推断 |
| M3 | 状态失效的爆炸半径由「依赖粒度」决定：对象级广播 → 属性级追踪 | ObservableObject + objectWillChange 是对象级广播：任一 @Published 属性变，所有读到该对象的视图陪跑重算（T4 Q2 实锤过）；@Observable 属性级依赖收集：读哪个属性依赖哪个，爆炸半径缩到属性。选型不再是「新 vs 旧」，是**失效粒度**这笔账 | KVO 本来就是属性级 did 语义——@Observable 反而是回到属性级，@Published 的对象级广播才是这条路上的「反常」一站 |
| M4 | Concurrency 性能模型：协作线程池 + hop 有价 + 取消是检查点协作 | 线程池大小 ≈ CPU 核数（对比 GCD 全局队列可线程爆炸——T3 Phase 3.4）；await/actor 切换是一次真实调度（hop 有开销，高频跨域调用要算账）；优先级反转在新世界有新形态（低优任务占着 actor，高优任务排队等）；取消不杀线程，靠 `Task.isCancelled`/检查点协作——检查点密度决定响应延迟 | GCD 里你管线程数、管锁等待；新世界把「线程」收走了，换成「hop 与排队」两笔新账——旧的「别在主线程阻塞」直觉仍然成立，只是阻塞的对象变成了隔离域 |
| M5 | 值语义是内存性能的默认红利，泄漏换了形态没消失 | struct/COW 消灭大量堆分配与共享可变（T1 Q2 亲手写过 COW）；但泄漏没绝迹——闭包捕获环、Task 生命周期持有、订阅凭证（T4 C1）、视图身份重建造成状态意外重置（不算泄漏但像泄漏）。OOM 方法论不变（峰值、增长斜率、大对象），排查对象多了 Task 与凭证两类 | 旧世界查 UIViewController 泄漏；新世界多查「这个 Task/订阅该死的时候死了吗」——deinit 打点的老手艺直接复用 |

学员自检要求：合上表复述 M1–M5，并把每个模型挂靠一条自己的旧世界经验（哪条旧结论迁移、哪条旧直觉会骗你）。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 性能工程是「规则先行」还是「度量先行」？**
- 正方最强论据（规则派）：大部分 SwiftUI 性能问题有成熟清单（LazyVStack、稳定 id、避免 GeometryReader 滥用……），规则前置比事后 profile 便宜；团队规范需要可执行的清单。
- 反方最强论据（度量派）：规则清单会诱导过早优化与「为规则而规则」；瓶颈位置靠猜的命中率低，Instruments 数据才是判决人。
- 对迁移者的意义：学员旧世界是度量派老手，本题看他会不会在新世界退化成「背清单的人」，或反过来无视清单。

**D2 @Observable 该不该作为迁移默认底座？（T4 D2 收口）**
- 正方最强论据：属性级依赖追踪直接消灭 objectWillChange 全广播的多余重算（M3 的账），与 async 协作更自然，Apple 投入方向明确。
- 反方最强论据：存量 ObservableObject 体量巨大；@Observable 无内建 publisher（防抖/节流管道还得回 Combine）；部署版本约束（iOS 17+）。
- 对迁移者的意义：T4 停在「机制对照」，本轮要补**对比实验**（同一状态变更模式下两边的失效次数差异）并给出按部署目标与管道需求的选型规则——不许停在「新的更好」。

**D3 Combine 管道的调试与维护成本算不算「隐性性能债」？（T4 遗留 5）**
- 挑战方最强论据：操作符链一长，断点打不进去、栈深不可读，排障时间就是性能工程的隐性成本——「调试体验」该进选型账本。
- 守方最强论据：管道声明式、行为可复现（给定输入序列输出确定），比散落的命令式回调更可测；调试工具（debug/print、OSLog）有成熟姿势。
- 对迁移者的意义：T4 D1「Combine 还有没有未来」的现实面——选型不光看能力，还看维护成本。学员 T4 Q1 管道四阶段打点的手感是本题原料。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只能复述定义 = 不过。每题配弱/中/强三级提示。

### C1 性能方法论：拿到一个「SwiftUI 列表卡顿」的工单，你怎么下手？（主场题）

问题：工单只有一句话「列表滚动掉帧」。说出你的完整分析路径：先怀疑什么、用哪些工具、拿什么数据、怎么判决。新旧世界各有什么变化、什么不变？如果 Instruments 在仿真环境跑不了，你的底线是什么？

- 弱提示：你旧世界处理 UIKit 列表卡顿的路径，哪几步是「工具无关」的？
- 中提示：帧成本三段（M2）——滚动掉帧可能卡在哪一段？Time Profiler 能看到哪一段、SwiftUI 模板（View Body 计数）能看到哪一段？仿真环境没有 Instruments 时，什么还能当硬证据？
- 强提示：路径：复现→分层定位（重算/diff/渲染哪段超预算，16.6ms）→Time Profiler 看 body 耗时、SwiftUI Instruments 模板看 View Body 重算次数与 diff 规模→定位到具体视图后按 M2/M3 动刀（身份稳定化/粒度细化/惰性化）→同口径复测。不变的是方法论（度量先于优化），变的是指标对象。仿真底线：可复现的计数/计时打点当硬证据，Instruments 类结论记「待真机验证」，不冒充。
- 评分要点：
  - 死记硬背典型：直接背「用 LazyVStack、加 id」清单——规则先行的病（D1 病灶）。
  - 真懂特征：先分层定位再动刀；新旧世界「方法不变、指标变」讲清；仿真底线（不冒充硬验证）主动说出。

### C2 SwiftUI 渲染：一帧的预算花在哪？（LazyVStack 与 body 的账）

问题：为什么 LazyVStack 比 VStack 扛长列表——它「懒」的是哪一步（body 重算还是渲染）？List 的复用和 UITableView 的复用是不是同一回事？ Equatable 视图 / `.equatable()` 省的是哪一步？「body 很便宜」这句话什么时候成立、什么时候骗你？

- 弱提示：UITableView 的 cell 复用省的是创建还是填充？LazyVStack 对「进入可视区域的行」才做的那件事，对应 M2 三段的哪一段？
- 中提示：VStack 一次性构建全部子视图的**值**（body 全算一遍）且全部参与布局渲染；LazyVStack 按需实例化可视区域——省的是渲染与布局，但可视区内状态失效照样重算。List 行视图本身不复用（值很便宜），复用发生在底层 UICollectionView 的 cell 承载层。「body 便宜」的前提是 body 里没有昂贵工作（格式化、排序、正则）。
- 强提示：`.equatable()` 在 diff 阶段短路：输入相等则跳过该子树的 body 重算与深入 diff——省的是重算+diff 两段，不省首次渲染。预算账：一帧 16.6ms（120Hz 是 8.3ms），滚动路径上每次状态变更都过一遍「重算×diff×渲染」，哪段超标治哪段。
- 评分要点：
  - 死记硬背典型：「LazyVStack 就是 UITableView 的 SwiftUI 版。」（复用机制说不清，省的是哪步说不出）
  - 真懂特征：「懒在渲染不在失效」讲清；List 复用的承载层差异说出；equatable 短路的位置（diff 段）对；body 便宜的边界条件给得出。

### C3 取消与检查点：一个「停不下来」的 Task（T3 遗留 3 + T2 遗留 1 回收）

问题：`task.cancel()` 之后 Task 为什么还在跑？取消信号到底送达了什么、没送达什么？检查点该插多密——给出一个可操作的密度原则。`.task {}` 修饰符的取消和手动 `Task {}` 的取消时机差在哪（T2 遗留钩子）？一个 `for await` 消费流时取消，桥的两头各自发生什么？

- 弱提示：T3 Q3 你撞过 actor 可重入——取消和可重入共享的底层事实是什么（await 处会发生什么）？
- 中提示：取消只翻转任务上的标志位（并把取消抛进挂起的 continuation/睡眠），**不会中断正在执行的代码**——所以只有检查点（isCancelled 判断、可取消的挂起点）能感知。密度原则：单次循环体代价大或要求秒级内停 → 每次迭代检查；循环体极轻且容忍百毫秒级延迟 → 按批次检查；检查点本身有开销（分支+读标志），不是越密越好。`.task` 绑定视图寿命（视图消失即取消，onDisappear 不用手写）；手动 Task 要自己取消，生命周期自己答（T4 C1 同款「寿命问题」）。
- 强提示：`for await` 中取消：AsyncSequence 迭代器抛 CancellationError（序列侧收到终止），生产者侧若用 AsyncStream 会收到 onTermination——桥两头的取消义务各自独立（T4 Q3 桥 B 的 finish 义务的近亲）。
- 评分要点：
  - 死记硬背典型：「cancel 了就立刻停。」
  - 真懂特征：标志位+检查点协作模型讲清；密度原则有成本意识（不是越密越好）；.task vs Task 寿命差异勾连视图生命周期；桥两头义务说出。

### C4 内存与 OOM：迁移之后泄漏换脸了（主场+新指标）

问题：值语义+ARC 之后，你预期内存问题是变多还是变少？说出三个新栈里依然会泄漏/涨内存的场景，各给排查手段。T4 C1 的「不存即取消」反过来问：**存住了但忘了一起了结**，是什么性质的问题、怎么查？Task 泄漏长什么样——和 UIViewController 泄漏的手法能复用吗？

- 弱提示：T1 你写过 COW——值语义消灭了哪类堆压力？哪类对象它管不着（引用类型成员、闭包捕获）？
- 中提示：三场景候选：①闭包捕获环（[weak self] 的老账新还）；②订阅凭证长寿持有（store(in:) 的 Set 跟着一个永不 deinit 的单例 → 订阅永生）；③Task 被长寿命对象持有且循环引用（Task 闭包强引用 self，self 又强引用 Task）。排查：deinit 打点（老手艺）、Allocations 增长斜率、`swift-nio` 式的任务计数打点。
- 强提示：OOM 方法论不变（峰值/斜率/大对象三看），新增两类排查对象：Task（「该死的任务死了吗」）与凭证（「该了结的订阅了结了吗」）。值语义红利要加限定：嵌套引用类型成员时拷贝不深（T1 的账），「struct 一定省内存」是新的迷信。
- 评分要点：
  - 死记硬背典型：「Swift 值语义不会泄漏。」
  - 真懂特征：三场景给得出且排查手段具体；凭证长寿问题能从 T4 C1 翻面推出；deinit 打点老手艺主动迁移；「struct 省内存」迷信主动破除。

### C5 actor hop 与优先级反转：新世界的两笔账（T3 遗留 2 回收）

问题：一次 actor 方法调用在性能上等于什么（对比一次锁的加解锁）？hop 的开销来自哪几件事？什么形态的代码会把 hop 开销放大成瓶颈、怎么收敛？优先级反转在 GCD 时代靠什么治、在 actor 世界以什么新形态出现、怎么缓解？

- 弱提示：T3 你讲过 actor ≈ 串行队列 + 锁——串行队列的「入队+出队」开销还记得吗？hop 比它多了什么？
- 中提示：hop 成本 = 离开当前执行上下文 + 调度到目标隔离域的执行器 + 排队（若 actor 忙）；高频小调用跨域（循环里逐条 await actor 方法）会把调度成本放大——收敛手段：批量化（攒一批一次过桥）、把热路径移进隔离域内、nonisolated 只读路径豁免。优先级反转旧世界靠优先级继承（QoS 传播）治；新世界新形态：低优 Task 占着 actor 执行长任务，高优 Task 在门口排队——缓解：拆短 actor 任务、关键路径显式优先级（Task(priority:)）、必要时换更细粒度隔离域。
- 强提示：量化直觉（供 Q2 校准）：单次 hop 微秒级，本身不可怕；可怕的是 N×hop（N 是调用频次）与排队放大。基准测试要控制变量：同等工作量下 actor vs NSLock vs 无同步，测吞吐与尾延迟，跑多轮取稳态。
- 评分要点：
  - 死记硬背典型：「actor 就是锁，性能一样。」或「actor 一定慢。」
  - 真懂特征：hop 三段成本讲清；放大形态（高频小调用）与收敛手段（批量化）成对给出；优先级反转新旧对照成立（继承机制 vs 排队形态）。

### C6 Combine 调试栈与性能：管道深了怎么排障？（T4 遗留 5 回收）

问题：T4 Q1 那条四阶段管道出 bug 时你怎么定位是哪一站的问题？Combine 的调试栈深（backtrace 全是框架帧）对排障成本的影响有多大、有什么实战姿势？这些成本该不该进「Combine vs async」的选型账本（勾连 T4 D1/D3）？

- 弱提示：T4 Q1 你每阶段打了时间戳和计数——如果没打，你现在还能定位吗？
- 中提示：姿势：`print()`/`debug()` 操作符逐站打事件流、边界处打时间戳与计数（Q1 手法）、缩小到单站后用最小复现拆开。栈深是真实成本：断点打不进操作符内部，崩溃栈难读；但管道行为确定性（给定输入序列输出确定）让「打点复现」比命令式回调更可操作。选型账本：能力（流算子）与维护成本（调试）两栏都记——T4 三轴判定管能力，D3 补维护成本栏。
- 强提示：工程结论：管道装配时顺手埋 print()/打点（像 Q1 那样），等于给每个工位装监控摄像头——调试成本前置到装配期，这是「声明式」付的税里可以报销的部分。
- 评分要点：
  - 死记硬背典型：「打个断点就行。」
  - 真懂特征：打点姿势具体（print/debug/时间戳/计数）；栈深成本与行为确定性两面都讲到；把调试成本写进选型账本的结论勾连 T4 三轴。

## 四、代码任务题（4 道，代码通道，挂项目 5.1/5.4 载体 + 前四主题总收账）

### Q1 视图身份与 diff 模拟器（载体 5.1 概念前置）

任务：CLI 无渲染，用纯 Swift 模拟 SwiftUI 的帧循环：定义行模型（id + 内容），写一个迷你 diff（按 id 配对，统计 新增/删除/原地更新/复用命中 四类计数）。跑三个场景对比：①稳定 id（后端 id）+ 头部插入一条；②不稳定 id（用数组下标当 id）+ 同样头部插入；③内容全不变只重排顺序。打印每场景的 diff 计数与「重建代价」（模拟：重建一行 = 一次昂贵初始化打点）。证明：不稳定身份把「原地更新」全部变成「删除+新建」。

- 脚手架：`struct Row: Identifiable`、`func diff(old:[Row], new:[Row]) -> DiffReport`。
- 评分要点：三场景计数对比成立（②的新建数暴涨）；能讲清「下标当 id 为什么是身份漂移」（C2/M2）；结论迁移到 List：为什么ForEach 要用稳定数据源 id。

### Q2 Actor vs 锁基准测试（载体 5.4 本体，T3 遗留 2 回收）

任务：同一工作负载（字典累加计数）三实现：actor 版、NSLock 版、无同步单任务基线。用 `withTaskGroup` 起 10 个并发任务、各写 2000 次，测总耗时与正确性（最终计数 == 20000）。追加「细粒度 vs 批量」对照：循环里**逐次** await actor 方法 vs 攒一批一次提交，测两者耗时比。多轮（≥3 轮）取稳态，打印每轮数据。

- 评分要点：三实现正确性全过（计数精确）；hop 放大效应实测出来（逐次 vs 批量的倍数）；能解释「为什么不能跑一轮就下结论」（预热/方差，M1）；优先级反转口述不强制实测（记为观察项）。

### Q3 取消延迟与检查点密度实验（载体 3.2 延伸，T3 遗留 3 + T2 遗留 1 回收）

任务：写一个长循环任务（如 10_000_000 次轻量迭代），三组检查点密度：①每次迭代检查 `Task.isCancelled`；②每 10_000 次批检；③不检查（对照组）。任务启动后 0.1s 发起 cancel，测量「cancel 发出 → 任务实际退出」的延迟。证明：密度越高响应越快但循环本体变慢，③ 组要么不停、要么退出延迟巨大。打印三组的循环耗时与取消延迟对照表。

- 评分要点：三组延迟对比成立；「检查点有开销」实测出来（①组循环总耗时高于③组）；密度原则（C3）能结合数据讲；`.task` 修饰符的寿命绑定口述勾连（T2 遗留 1 清偿）。

### Q4 收账四连：背压 Subscriber + values 桥 + @Observable 对比（T4 遗留 1/3/4 总收账）

任务：三段。段一（T4 遗留 1）：写自定义 `Subscriber`（实现 receive(subscription:)/receive(_:)/receive(completion:)），订阅时报**有限需求（.max(2)）**、每处理一个按需追加 .max(1)、处理间 sleep 制造慢下游——用 print 证明上游是「按需求发货」而非灌满。段二（T4 遗留 4）：把段一的 publisher 用 `.values` for-await 消费一遍，与 sink 版对拍事件序列；说出两条消费路径的寿命管理差异（cancellable vs 迭代器生命周期）。段三（T4 遗留 3，D2 收口）：`ObservableObject` 与 `@Observable` 各写一个双属性模型，模拟「改属性 A」各打点依赖方收到的失效通知次数（ObservableObject 走 objectWillChange 计数；@Observable 无 withObservationTracking 则在 CLI 用 sink/计数近似并如实说明局限），对比爆炸半径。

- 评分要点：段一有限需求行为打点成立（上游发货节奏跟着 demand 走）；段二 values 桥跑通且寿命差异讲得出；段三对比结论与 T4 C6 口述一致，局限如实声明（@Observable 观察 API 在 CLI 的可用性以实测为准，不可得就用次级证据并说明）。
